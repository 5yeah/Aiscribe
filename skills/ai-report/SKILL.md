# AI 日报/周报生成方法论（ai-report）

本 Skill 只承载**方法论与输出规范**，取数能力由 `aireport` MCP 服务提供。
两者分工是这套方案的核心：**工具负责“一条不漏地取回真实对话”，你负责“读懂并归纳”**。
不要让工具直接吐模板给你，也不要自己凭记忆编造当天的工作。

## 一、前置检查

1. `list_sources`：确认本机数据源可用性与会话数。
   某来源 `available=false` 属于正常（该工具没装/没用过），**在报告的数据来源里注明跳过即可，不要报错中断**。
2. 若 MCP 不可用，降级为 CLI：`python -m ai_report daily --date <日期>`（只到“任务列表级”，需在报告里说明）。
3. 用户已经用过本地引导页（`python -m ai_report ui`）时，他会直接发来一段“交给 AI 的指令”，
   里面已带好窗口与勾选的记录 id。**这时跳过摸底，直接按指令取数**，第 2 步只取指令里列出的 id。
   （若他在引导页点的是「生成报告」，报告已经落盘到 `reports/` 了：正文是纯模板草稿，
   若本机配了 LLM Key，则已是「程序定结构 + AI 只改写条目文字」的版本 ——
   他再发指令过来就是要你按同一份素材归纳出质量更高的版本，覆盖写同一文件即可。）

## 二、取数：先摸底，再精读

按顺序调用 `get_conversations`，不要一次就把所有内容全量拉进上下文：

| 步骤 | 调用 | 目的 |
|---|---|---|
| 1 | `{mode:"daily", date:"YYYY-MM-DD", detail:"summary"}` | 摸底：当天有哪些项目、大概多少条记录 |
| 2 | `{mode:"daily", date:"YYYY-MM-DD", project:"<项目名>", detail:"full"}` | 逐个项目精读原始输入全文 |
| 3 | 需要跨天时 `{mode:"range", start, end, detail:"full"}`；周报用 `{mode:"weekly", date}` | 周报/区间汇总 |

- 项目多于 4 个时，逐个项目分开取，避免一次性塞满上下文导致后段丢失细节。
- 数据量很小（≤5 条记录）时才可直接 `detail:"full"` 一次取全。
- **每条素材的 `messages` 带 `role`**：`user` 是用户的诉求，`assistant` 是 AI 当时的结论与改动。
  写"做了什么"要看 `assistant` 那侧，别只把用户的话改写成完成态（那是编造）。
  两条消息时间戳相同时，`user` 在前、`assistant` 在后，按这个顺序读。
- **按勾选过滤**：引导页传来的指令里有 `ids`，用 `get_conversations(..., detail:"full", ids=[...])`
  只取这些记录；用户没勾的就当不存在，不要用“全窗口”覆盖他的选择。
- **素材可能已被剪辑**：返回里带 `trim: {start, end}` 的记录，表示用户在引导页给它设过起止时间，
  工具**已经**把窗口外的片段丢掉了（`detail:"full"` 时窗口内一条不剩的记录会直接不返回）。
  直接按拿到的内容写，不要去找回被剪掉的部分，也不要换成整段原文。
- 取数窗口由工具按**北京时间**计算，你**不要自行扩大或缩小窗口**。

## 三、归纳准则（硬规则，逐条遵守）

1. **只写窗口内的事**。哪怕你在素材里看到昨天或上周的内容，也不能写进今天的日报；
   跨天会话由工具按“发送日”切分，你要尊重这个切分。
2. **项目归属以工具返回的 `project` 分组为准**。同一项目的多条会话要合并成一个项目段落；
   若你判断两个分组其实是同一个项目（例如目录名与习惯叫法不同），可以合并，并在项目名下用一句话说明。
   **禁止按会话标题里的关键词改归类**：本工具内部日记的会话标题常写着「汇总 A/B/C 三个项目…」，
   那是**在讲别的项目**，该会话仍属工具自身项目（如 `Aiscribe`），不能因为它提到某个项目名就塞进那个项目段。
3. **一条“事项”= 一个可交付的工作主题，不是一条会话、更不是一条消息**。
   同一主题的多次追问、报错、反复调整，必须合并成一条事项，把进展与结论写进去。
   **同一件事的素材出现在两条不同会话里（同一句提问、同一张图被问了两次），只能写一条事项**，
   不得拆成两条；条目总数应当 ≤ 素材里的实质主题数，而不是会话数。
4. **不编造**。只依据素材原文；素材没提到的结论、数字、人一律不写。
   不确定的地方写“（待确认）”，而不是猜。**特别注意截图旁的一句话**：
   「`[图片]` RabbitMQ 崩溃了」是用户在标注现象/猜测，只能写成
   「排查前端不显示（用户判断为 RabbitMQ 崩溃）」，**不能写成「定位为 RabbitMQ 崩溃所致」**；
   同理「这些文件其实是能 ls 读取的」是用户的断言，不是你的验证结论，
   不要写成「验证了文件读取方式对流程的影响」。
5. **剔除噪声**：客套话、纯操作指令（“继续”“再改一下”“用中文回答”）、图片占位符、日志报错栈
   不作为独立事项；但报错修复本身是有价值的事项，要写成一件事（现象 + 处理 + 结论）。
   **整条会话清洗后只剩「请继续执行未完成的任务」这类口头指令时，当天该会话没有实质内容，不出事项**
   （这类“只发了继续”的会话很常见，不要为了凑条目把它写进去）。
6. **写人话，不搬原文**。事项名用名词短语（10～20 字），说明用 1～3 句话讲清“做了什么 / 结论是什么”，
   可以保留关键的模块名、参数、时间点、报错原文，但不要整段粘贴。
7. **待办**：素材里出现“下一步 / 未完成 / 待验证”时，归入报告最后的“待办事项”，一条不超过 20 字。
8. **已被剪辑的素材不可“复原”**。带 `trim` 的记录，其窗口外片段是用户主动丢弃的，
   不能再写进报告；若素材恰好全被剪掉（工具也没返回它），就当这条不存在。

## 四、输出格式规范

### 4.0 先确认有没有「格式克隆」模板（优先于下面的默认骨架）

1. 调用 `list_templates`：看用户是否上传过他以前的日报/周报样例（引导页「格式克隆」学到的）。
2. 若存在模板，调 `get_format_spec(name)` 拿到规范，**本次输出以模板规范为准**，
   下面的默认骨架只作为兜底参考。
3. 模板里 `pending_vision=true` 表示样例是图片、工具未做识图：
   若你有读图能力，先看清图片排版，再用 `save_template({name, features})` 把结构回填
   （只写结构，不要写样例里的具体工作内容），然后重新 `get_format_spec` 取规范。
4. 学到的模板**只决定排版**：项目名、时间行、事项标记、是否双版本等；
   **具体内容仍必须来自本次素材，绝不能照搬样例里的旧内容**。

没有模板时，用下面的默认骨架（上半详细版，`---` 分隔，下半简洁版）。

```markdown
# AI 日报 2026-10-16

**汇报人：** <姓名> ｜ **部门：** <部门> ｜ **日期：** 2026年10月16日

> 数据来源：<来源1 的取数口径>、<来源2>、<来源3>（本地聚合，隐私优先）

**1、项目名称（上下文，09:06–22:08）：**

①、事项名：这一条讲清做了什么、结论是什么。

②、事项名：……

**2、下一个项目：**

①、……

**7、待办事项：**

①、……

---
*本报告由 AI 阅读本机原始对话后归纳生成。*

---

# AI 日报（简洁版）2026-10-16

**1、项目名称：**

①、事项名

②、事项名

**2、下一个项目：**

①、事项名
```

### 格式硬要求

- 项目用 `**1、项目名称：**` 起头（阿拉伯数字 + 顿号），事项用 `①②③…`（带顿号 `、`）。
- **详细版**项目名后允许跟“（上下文，起止时间）”；**简洁版一律去掉括号内容**。
- **简洁版**每条只保留详细版里 `①` 冒号**之前**的那句事项名，冒号后的说明**全部删掉**。
- **每条事项下面不要再写「时间：」「来源：」「状态：」之类的元信息行**（用户 2026-10-18 明确要求）：
  报告要简洁，来源只在头部 `> 数据来源：` 那一行统一标注，不要逐条重复时间与来源。
- 项目之间空一行，事项之间空一行；不要用 Markdown 的 `###` 层级标题来写项目。
- 无当日数据时，写“今日无 AI 会话记录”，不要空文件、不要编造。

## 五、落盘

1. `save_report({markdown, filename:"日报_YYYY-MM-DD", format:"md"})` → 保存 Markdown（默认，便于二次编辑）。
2. 用户要 Word 时再调一次同一份 `markdown`，`format:"docx"`（文件名同 stem）。
3. 用户要**可分享的网页**时用 `format:"html"`：生成的是**自包含单文件**（样式内嵌、无外部资源、无脚本），
   可以直接双击打开、丢进 IM 或发给同事看；不支持 Markdown 的接收方用这个最省事。
4. 三种格式都只用同一份 `markdown`，不要为不同格式重写正文。
5. 落盘后回复用户：**文件路径 + 该项目条数概览**，不要把正文再贴一遍。

## 六、交付前自检（逐条核对）

- [ ] 报告里出现的每个事项，都能在 `get_conversations` 的素材里找到出处
- [ ] 没有把一条素材写成两条事项（同一件事在两条会话里出现过，只算一条）
- [ ] 没有按标题关键词改归类（提到别的项目的会话没被塞进那个项目段）
- [ ] 截图旁的一句现象/猜测没有被写成「已定位 / 已验证」的结论
- [ ] 只发「继续」这类口头指令的会话没有单独占一条事项
- [ ] 有格式模板时，排版已按 `get_format_spec` 的规范复现（没有照搬样例里的旧内容）
- [ ] 没有任何窗口外的时间内容混进来
- [ ] 项目名与工具分组一致，没有把两个项目混在一段
- [ ] 详细版 / 简洁版都在，简洁版没有括号、`①` 后没有内容
- [ ] 每条事项下没有「时间：」「来源：」「状态：」等元信息行（只在头部保留一行数据来源）
- [ ] 数据来源行如实标注了哪些源可用、哪些跳过
- [ ] 带 `trim` 的素材只写了窗口内的片段，没有把被剪掉的内容补回来
- [ ] 待办事项只保留素材里真实存在的未完成项

## 七、隐私红线

- 原始对话只在本机读取，**不要上传**，也不要写进报告以外的文件。
- 报告只落本地 `reports/` 目录；除非用户明确要求，不发送到任何外部系统。
- 只有生成好的**报告正文**（已非原始对话）在用户主动开启 `--llm` 润色时才会发往 LLM 端点。
